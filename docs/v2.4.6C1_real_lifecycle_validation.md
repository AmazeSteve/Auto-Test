## C1 与 C2

C1 只面向一次正常 Modify → Verify → Rollback → Verify Rollback。
不实现真实超时、连接重置、HTTP 500 或回滚失败注入；这些属于以后单独批准的 C2。
B2 离线测试已覆盖未知状态、异常和清理执行机会。C1 的异常单元测试全部使用假 transport。
没有新增 CaseRunner dry-run 模式、DSL、Effect 状态或手工生命周期状态机。

## 显式目标与依赖

只允许隔离的专用测试用户；操作者须确认它不是管理员、活跃培训用户或真实业务用户。
`TEST_USERNAME` 必须显式设置，不能使用框架默认用户名。返回 Read Model 的
`usr_ste_usr_id` 必须与其完全一致。不要把账号密码、Cookie 或用户数据写入本文件。

依赖沿现有 YAML 自动排序：`WB_USER_GROUP_001` → `WB_USER_GROUP_004` → `WB_USER_004`。
然后通过 root 的现有 Before Capture 获取完整表单。没有复制业务 endpoint URL。
这里“只读”指业务语义：现有表单读取接口采用 POST，但不修改业务状态。
目标必须能被现有配置的用户组查询及第一页用户列表定位；找不到即停止，C1 不改分页或用户组配置。

## 人工只读 Preflight

以下命令仅供将来人工在已配置的本地环境运行，本轮 Cloud 不执行。
先安全配置现有 `configs/env.local.yaml` 和管理员登录凭据，再在 PowerShell 设置目标：

```powershell
$env:TEST_USERNAME = "YOUR_ISOLATED_TEST_USERNAME"
$env:TEST_PREFIX = "AUTO_TEST_C"
python -m pytest tests/test_05_user_update_preflight.py -q --env local
```

入口在请求登录 fixture 之前检查显式目标。随后只执行现有只读依赖与 Before Capture，
调用冻结 Resolver/Builder 生成计划，不调用修改接口，也不创建敏感恢复 journal。
确认 27 字段 baseline/mutation、JSON 恢复 envelope、唯一的 `usr_display_bil` diff，
以及完整 baseline 和恢复材料等价。禁止字段由冻结 Write Model whitelist 排除。

证据只有 Case ID、目标哈希、字段数量、changed fields 和三个 SHA-256；
`READY=YES` 只表示 Preflight 完成，不表示真实生命周期验证成功。
mutation 仍使用 `$data.unique_display_name`，不是固定字符串。

## 将来人工授权的一次真实生命周期

须同时满足四道门禁，缺失任一项就在获取登录 fixture 前跳过：

1. `--allow-destructive`。
2. `--allow-c1-real-lifecycle`。
3. 明确设置非空 `TEST_USERNAME`。
4. 明确设置 `C1_CONFIRM_USERNAME`，且与 `TEST_USERNAME` 完全相等。

人工完成 Preflight 审查、确认测试用户无并发修改、没有待处理 recovery journal 后，
才可以在本地单独选择验收文件运行。以下命令不是本轮 Cloud 的授权：

```powershell
$env:C1_CONFIRM_USERNAME = $env:TEST_USERNAME
python -m pytest tests/test_06_user_update_lifecycle_acceptance.py -q --env local --allow-destructive --allow-c1-real-lifecycle
```

入口复用 `LifecycleRunner.run_lifecycle`，临时观察 Before、Resolver 和 After，返回原对象，
不改其状态机。其成功返回后再追加一次只读表单 Capture，验证完整 27 字段恢复状态。
正常 pytest 在缺少任一真实写门禁时不会执行这个 C1 生命周期。

## 业务状态与成功条件

投影调用冻结 Builder：`mutable_fields=set()`、`overrides={}`，使用它的 baseline，
不复制 27 字段映射。`cur_lan` 来自 root Builder arguments；Read Model 的 `curLan: null` 合法。
只把 `roleCode/tagId/directLeaderId` 的逗号文本拆分、trim、去重排序为无序集合。
其他字段保留原值和类型；`None` 与空字符串、日期差异、组/职级/岗位及 SSO 差异均有意义。

验收通过必须同时满足：已有生命周期成功返回；Effect 为 `restored`；
mutation semantic diff 恰好是 `usr_display_bil`；最终恢复 semantic diff 为空；
Context 中仍保留与 journal 一致的 27 字段恢复材料。
只读最终 Capture 和全字段比较不能由原 YAML 中少量字段断言替代。

## Recovery journal

验收包装器先调用原 Resolver，核对其实际恢复 envelope，再在 mutation 发出前写入
`.runtime/recovery/<case-id>-<unique-id>.json`。这是实际发送所需的同一份标准化 baseline，
不是前置查询的较早 Snapshot。journal 的 `prepared` 是磁盘记录状态，**不是新增 Effect 状态**。

JSON 含 schema version、创建时间、B2 base commit、目标哈希、恢复 envelope 哈希和实际 27 字段 body。
只允许 whitelist，不写 Cookie、Authorization、密码、管理员凭据或 token。
敏感文件使用同目录临时文件，flush、fsync 后 atomic replace；临时文件具备平台支持的私有权限。
使用不同文件名保存每次调用，不覆盖旧恢复记录。目录被 Git 忽略，禁止放入文档或 Allure 输出目录。
Journal 拒绝仓库中 `.runtime` 之外的存放目录；离线测试的目录注入仅使用 checkout 外的临时路径。
开始真实 lifecycle 前会强制检查已有正式 JSON journal；`create()` 也再次检查。
只扫描文件名和文件元数据，不读取 payload；任何正式 JSON 都视为待处理记录，拒绝新的写验收，
只报告数量及目录，不创建第二份 journal，也不删除旧记录。`.journal-*.tmp` 不计为正式记录。
这是顺序执行的 safety gate，不是并发锁或自动 recovery/replay。只读 Preflight 可继续，但保留旧 journal。

所有生命周期、语义检查和最终证据输出成功后，才删除敏感 journal。
异常、最终业务漂移、journal/证据错误、进程中止时保留已经写好的 journal，并报告路径。
成功摘要附件记录的是删除前的 `prepared` 状态；成功返回值记录 `deleted`。
进程崩溃无法保证运行时 finally 执行；下次操作前必须人工检查该目录。

journal **含敏感用户资料**：只在安全本机检查，禁止打印 payload、上传 Allure、加入 Git，
或未经审查作为请求重放。它不含登录凭据，也不提供自动恢复命令。
发现残留时停止新的写验收，由操作者确认当前业务状态和恢复方案；不要自动删除残留。

## 证据与人工停止清单

C1 作用域屏蔽旧运行时 body/Context 附件及含业务 ID 的动态请求 step 标题，
仅输出 C1 安全摘要、字段名 diff、哈希、Effect 状态及 journal 路径。
观察保留在内存，完整 Before/Mutation/Restore 不再引入 Allure。

出现目标身份不匹配、非目标字段变化、缺少恢复材料、状态不是 restored、
最终 diff 非空或存在待处理 journal 时，停止；不扩大到 C2 或再次试写。
隔离用户和无并发修改仍是人工前提：回滚可能覆盖外部同时发生的修改，审计记录不会回退。
