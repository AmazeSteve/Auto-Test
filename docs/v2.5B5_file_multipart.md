# v2.5B-5 File Reference & Multipart Safety Foundation

This foundation adds offline-tested, static file references to YAML Cases. It
does not add a real WizBank upload Case or adopt multipart in business YAML.
Requests continues to own multipart encoding and boundary generation.

## Compatibility decision

Legacy raw `files` passthrough is no longer a supported YAML contract. In older
versions, `files` was passed through `VariableResolver` and could contain raw
Requests objects. B5 intentionally tightens that behavior to the descriptor
schema below. Existing JSON resolution and data-only behavior are unchanged;
`request_builder` and `restore_payload` remain JSON-only.

```yaml
data:
  title: "{{title}}"
files:
  upload:
    fixture: course/demo.pdf
    filename: demo.pdf
    content_type: application/pdf
```

`files` is a Mapping of distinct multipart field names to descriptor Mappings.
Only `fixture` (required), `filename` (optional), and `content_type` (optional)
are accepted. Raw strings, bytes, file objects, Requests tuples, descriptor
lists, and unknown descriptor keys are rejected. Different file fields are
supported; multiple files under one field are not.

## Static references and filesystem boundary

Production file lookup uses only `<repository>/data/files/`. A YAML Case cannot
select a root, use the current directory, home directory, or fetch a remote
file. No fixture-root directory is needed for Cases without files. A file Case
fails closed if that root or the referenced file is unavailable. Tests can
replace the root with an isolated temporary tree.

A fixture reference is a static relative POSIX path. Unicode and spaces are
preserved without normalization. Each component must be nonempty and cannot be
`.` or `..`; absolute paths, Windows drive forms, UNC/extended paths,
backslashes, colons, and variable expressions are rejected on every platform.
Actual directory entries must match the reference's case exactly, including on
case-insensitive filesystems.

The resolver rejects detected symlinks, junctions, and reparse components,
checks canonical containment in the fixed root, opens a validated readable
regular file immediately in `rb`, and verifies the opened object is regular.
Directories and special files are rejected. Detected canonical escapes always
fail closed. This is not a sandbox against hostile concurrent filesystem
mutation.

`filename` defaults to the fixture basename. An override is a static nonempty
basename: no separators, colon, dot/dot-dot, control characters, or variables.
An explicit `content_type` is static, nonempty, and has no control characters.
There is no MIME guessing or automatic `application/octet-stream`. Omitting
MIME omits an explicit part Content-Type.

## Multipart body and header rules

Supported body states are no body, JSON, data, files, data plus files,
`request_builder`, and `restore_payload`. Other combinations remain invalid.
GET body restrictions remain in force. Effect capture before/after requests
cannot contain `files`; this version does not support Effect multipart capture
or multipart Lifecycle recovery.

When files are nonempty, resolved `data`, if present, must be a Mapping of
nonempty static string keys to scalar values or lists of scalars. Scalars are
`str`, `int`, `float`, and `bool`. None, bytes, nested mappings/collections,
file objects, and arbitrary iterables are rejected. Ordinary form values still
use `VariableResolver`, and the final shape is checked after resolution.
CaseRunner passes multipart form data to transport as an already resolved
Mapping, preventing ApiClient from interpreting its values again and changing
that validated shape; data-only resolution keeps its previous behavior. No
part of a files descriptor is resolved as a variable.

With nonempty files, both `ApiClient.default_headers` and effective Case
headers must omit Content-Type, case-insensitively, regardless of its value.
Requests generates a new multipart boundary and the corresponding header; the
framework neither supplies nor caches it. ApiClient itself is unchanged.

## Resource ownership and safe evidence

FileResolver owns all handles. CaseRunner owns the resolver context lifetime;
ApiClient borrows handles, and Requests reads them. Files open after principal,
credential, variable, header, Effect-before, builder, and multipart guards.
Partial-open failure closes previously opened handles. Every exit from the
request scope closes all handles before Effect-after, assertions, or extract,
including preparation, evidence attachment, and send failures. Cleanup does
not depend on garbage collection, Session close, or ApiClient close.

File evidence contains only `field`, `filename`, `size`, and `content_type`
(null when omitted). It contains no bytes, preview, base64, logical fixture
reference, absolute/canonical path, root, or file-object representation. No
SHA-256 is calculated and no file is pre-read merely for evidence. Binary
content is passed without decoding, encoding, or newline conversion.
Filesystem/read failures have stable safe errors, and borrowed handle
representations omit private paths. Safety tests cover ordinary exception
strings, default pytest failure output, and captured Allure attachments. This
does not claim safety for every nondefault traceback mode such as
`--showlocals`.

## Validation boundary and limitations

The implementation is validated with temporary binary fixtures, real Requests
preparation, and fake Session transport, with real sockets rejected. It makes
no claim that a real WizBank endpoint accepts these uploads.

Controlled Validation is **NOT REQUIRED** for this foundation because there
are no real upload Cases or business YAML adoption. Before first claiming real
WizBank multipart interoperability, Controlled Validation is **REQUIRED**;
prefer a temporary disposable resource. Persistent-resource uploads require a
separate cleanup/Lifecycle review.

Known limitations are same-field multiple files, streaming/chunked multipart,
dynamic/generated/remote files, custom part headers, automatic MIME/hash
evidence, hostile filesystem TOCTOU sandboxing, and unproven real WizBank upload
interoperability. Link/reparse creation depends on platform capability; an
unavailable platform capability is not evidence that its real behavior passed.
